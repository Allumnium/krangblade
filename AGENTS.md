# Warbound — standing project instructions

Read this file, [TODO.md](TODO.md), [THOUGHTS.md](THOUGHTS.md), current repository state, and outstanding pull requests at the beginning of every Warbound development chat/session. Later explicit user directions take precedence over these notes and older README sections.

## Workflow
- Use tabs for leading indentation in all GDScript (`.gd`) and Godot shader (`.gdshader`) files, with a display width of four columns. Do not mix tabs and spaces in indentation. CI checks tracked scripts and shaders; preserve non-indentation whitespace and follow `.editorconfig` in external editors. In Godot, set Text Editor → Behavior → Indent → Type to Tabs and Size to 4.
- Apply the `skip-ci-docs` PR label for documentation-only changes to README.md, AGENTS.md, TODO.md, THOUGHTS.md or THOUGHTS_ARCHIVE.md. CI verifies the entire diff is limited to these files and the mandatory version-only bump in project.godot; any other change runs full validation. The required `validate` check and version checks are never skipped. Do not use commit-message CI skip directives.
- Temporary fast-iteration mode (user-requested): CI is manual-only. Do not wait for CI before merging or pushing development changes. Preserve versioned squash titles. Keep local/static checks when practical; report unvalidated changes accurately. Restore automated CI when the user requests it.
- Every Warbound project conversation is a development-enabled session. Use the GitHub connector directly; discover and attempt its tools before claiming a limitation. Never ask the user to switch sessions merely to access the repository.
- The game is **Warbound**. The repository is Allumnium/krangblade; the integration branch is main.
- GitHub connector access has repeatedly worked for reading, creating commits, pushing branches, and merging pull requests. Discover and attempt the actual GitHub tools before declaring access unavailable. If a call fails, inspect the error and try an appropriate alternative; report the specific blocker only if access really fails. Never fabricate a push or a test result.
- For approved implementation requests, make the changes in the repository rather than returning speculative code snippets or asking the user to apply them manually. Commit and push, open a PR, and merge without waiting for CI during temporary fast-iteration mode. Resolve any outstanding PR/checks before building on them. Verify the actual main-branch commit/version and distinguish a pushed branch, merged PR, and validated main branch.
- Increment application/config/version in project.godot in **every commit** using MAJOR.MINOR.PATCH, including follow-up and documentation commits. Main menu reads the same value. Patch for fixes/adjustments, minor for features, major for significant breaking milestones. Preserve CI version checks.
- Every commit message subject must start with the exact resulting application/config/version from project.godot, prefixed with `v`, followed by a colon and a concise description (for example, `v0.4.4: Require versioned commit messages`). This applies to all commits, including fixes, documentation, follow-ups and squash-merge commit titles. When merging, explicitly preserve the final version in the commit subject.
- Godot 4.7 project (CI currently 4.7.2). Keep direct-IP ENet multiplayer usable without Steam for development; Steam integration is a future goal. Preserve one to eight players, lobby chat, and offline AI setup. Agreed direction supersedes fixed teams: migrate to independent bilateral diplomatic relationships, including overlapping mutual alliances and multi-sided wars. Until migration, existing team-based rules remain legacy implementation, not the target design. Do not invent AI strategy or military/gameplay systems that have not been agreed.
- Host/solo authority owns simulation changes. Validate ownership, targets, inputs, and request permissions at the authority; keep local UI and remote snapshots consistent. Extend actual two- and three-peer ENet regression coverage for new commands. Check parsing, imports/metadata, economy, solo, network and disconnect/restart behavior. Do not equate a headless pass with visual or internet-latency verification.
- Avoid flaky fixed waits in multiplayer tests; wait for meaningful synchronized state and completed peer checks. Investigate gameplay and network failures instead of weakening assertions. Track Godot .uid/.import sidecars where applicable. Do not commit editor caches.
- Keep status reporting concise: version, what changed, what passed, whether pushed/merged, and genuine limitations. Do not make the user repeatedly ask whether a commit was pushed. Do not claim to continue work asynchronously.

## Code organization and pre-edit protocol
- Keep README architecture diagrams and examples independent of leading whitespace where practical; Godot editor indentation normalization can cause repeated local changes. Prefer plain Markdown relationships over space-aligned diagrams.
- Read the current [source ownership map](README.md#source-ownership-map) before editing. Search the repository for existing definitions AND call sites (including aliases, tests, AI and Codex) before adding a helper, constant, state field, RPC or command. Extend the existing owner instead of copying behavior into another layer.
- Single sources of truth: simulation owns rules, recipes, eligibility, relationships, canonical state and mutations; session owns authority dispatch, RPCs, timing and replication; client owns input, presentation and visual-only caches. UI calls read-only rules for previews and requests commands through GameSession. AI uses the same validated rules as humans. Do not add a second authoritative state or local gameplay calculations.
- Keep domain modules cohesive, use explicit dependencies and public query/command interfaces; do not create circular preloads, generic dumping-ground utility files, or new UI calls to private rule helpers. Keep existing entry points stable during extraction. Record which module owns each new dictionary field and its serialization/reset lifecycle.
- Organize each script in clearly named functional sections: dependencies/constants, owned state, lifecycle, public API, grouped private helpers. Prefer small single-purpose functions (review functions over ~80 lines or scripts over ~1,000 lines for natural boundaries, not hard limits). Use descriptive role-specific locals (e.g. rogue_event vs destruction_event), avoid shadowing/redeclaring names within a function, and prefer typed parameters and return values where practical. Scan the entire changed function, not just the edited lines; do not claim a text scan is a parser.
- Extract one coherent domain at a time in behavior-preserving PRs, keeping deterministic iteration, simulation order, stable IDs, hot-loop allocations, cache invalidation, RPC names/signatures and snapshot schema unchanged. Do not combine restructuring with balance, UI redesign or unrelated feature changes. Include new modules in Godot parse coverage; run the existing import, parse, gameplay, solo, ENet and relevant benchmark checks whenever practical. In manual-only CI mode explicitly report unrun checks; no claim of runtime validation without actual execution.
- Update the source map as responsibilities move. Before adding a test, locate the existing domain fixture; add a focused semantic scenario rather than another copy of setup or a presentation assertion.

## Automated testing scope
- Do not create or require UI-centered unit or regression tests that assert widget names, hierarchy, labels, positions, dimensions, visibility, tabs, styling, or other presentation details. The UI is expected to evolve frequently. Retire obsolete presentation-only assertions rather than maintaining them after each redesign.
- Test gameplay semantics directly against the simulation and authoritative commands: ownership, costs, refunds, movement, combat, logistics, replication and lifecycle. Keep script parsing, resource import/metadata, startup, solo and real two-peer ENet checks mandatory on non-documentation changes. Extended coverage is scope-selected.  Test scene startup/lifecycle without asserting UI layout. Verify visual design and interaction through manual playtesting; report when unavailable.

## Roadmap and ongoing observations
- Maintain the in-game Warbound Codex ([scripts/codex.gd](scripts/codex.gd)) with every game change. Before committing, review all affected articles and update or remove outdated rules, controls, costs, charts, tables and examples in the same commit; if nothing player-facing changes, verify that the guide remains accurate without making artificial edits. Keep all player-facing Codex text as short and minimal as possible: use brief factual descriptions, concise labels, icons, tables and diagrams instead of long paragraphs, redundant explanations or filler. Derive numerical content from authoritative game constants wherever practical. Do not document unimplemented features as available.
- Maintain [TODO.md](TODO.md) as the living, prioritized roadmap of agreed work and explicitly labeled unresolved design questions. Review dependencies and current implementation before starting tasks. Update it in the same change as relevant implementation or design decisions; check off items only after their acceptance criteria and required validation are met. A roadmap entry is not blanket approval to implement unresolved mechanics or unrelated work.
- Maintain [THOUGHTS.md](THOUGHTS.md) proactively during every development session. Record concise observations of potential bugs, UX friction, gameplay issues, technical risks and ideas that could improve the game, including those noticed while working on unrelated tasks. Distinguish verified issues from hypotheses and proposals; include useful context, possible remedies and references. Deduplicate and refresh existing entries rather than accumulating stale notes.
- Thoughts are suggestions for review, not authorization to implement new mechanics. Promote agreed actionable items into TODO.md, preserving a link or identifier where useful. Keep promoted thoughts active until resolved; move completed/resolved thoughts out of THOUGHTS.md into [THOUGHTS_ARCHIVE.md](THOUGHTS_ARCHIVE.md), with date, outcome and version/PR or other evidence where applicable. Do not delete their history; record rejected/superseded ideas with their disposition rather than marking them implemented.
- Review the roadmap and active thoughts before finishing each change. Keep all three files current in the repository and include their updates in the normal versioned commit/PR workflow. Do not postpone maintenance to another chat.
